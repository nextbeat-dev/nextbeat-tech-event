## 3. bench:redos の n 安全運用表

前提: 標準 RegExp 側は1文字ごとに約2倍（n+2 で約4倍）で重くなる。絶対値はマシン依存で数倍変動するため、**相対則を主に説明する**。

### 表1: 標準 RegExp 側（イントロ実演・②完了後の実演で使用）

| n | 目安（相対則からの推定） | このマシンでの実測 | 運用 |
|---|---|---|---|
| 20 | 最速（数十ms未満） | — | 自由 |
| 22 | 数十ms | — | 実演1段目 |
| 24 | 1秒未満 | — | 自由 |
| 26 | 数秒 | **2192ms（≈2.2秒）** | 実演2段目（デフォルト値） |
| 28 | 一桁秒後半〜十秒弱 | — | 実演3段目・ライブの実用上限 |
| 30 | 数十秒 | — | 時間が余った時のみ・1回だけ（打つ前に「30秒前後返ってきません」と宣言） |
| 32 | 1〜2分台 | **93097-93203ms（≈93秒）** | `--force` なしでは実行不可（ガード）。実行するなら講師のみ、Ctrl-C 前提 |
| 34 | 数分〜十分 | — | **絶対禁止** |

**注記（重要・当日リハで必ず上書き）**: 「このマシンでの実測」は教材開発機での値で、README 旧参照値（n=28≈8.8秒）よりこの開発機は遅い（n=26で既に2.2秒）。**講師の当日実マシンで n=22/26/28 を実際に叩いて数値を確定し、この表とスライドの数値を上書きすること。** 絶対値ではなく「n+1で倍、n+2で4倍」という相対則を軸に説明すれば、マシンが変わっても破綻しない。

### 表2: 自作エンジン側・正規化なし（①後②前の動機付けデモ、パート3で使用）

`bench/redos.ts` と `bench/linear.ts` にはどちらも「12文字プローブ」による安全装置が実装済み: `n` の値によらず、まず `"a".repeat(12)` で状態数を確認し、`stateCount() > 6` なら**その場で打ち切って**メッセージを出す（正規化なしだと12文字時点で13前後まで膨れる）。つまり **①後②前の状態では、どんな n を渡しても計測前に安全に打ち切られる**（OOM・フリーズは起きない）。

だからパート3で `n=16` を指定するのは「クラッシュを避けるため」ではなく、**進行のペース配分のため**:
- `bench:redos` は先に `[1] 標準 RegExp` 側を（ガード無しで）実行してから `[2] 自作エンジン` 側に進む。n=16 ならこの `[1]` 側が数ms〜十数msで一瞬で終わり、体感時間を消費せず `[2]` の「状態爆発を検知」メッセージにすぐ辿り着ける
- n=26（デフォルト・引数省略）だと `[1]` 側だけで約2秒待たされ、イントロで既に見せた「固まる標準RegExp」を意味もなく再演してしまう（時間の無駄・メッセージの重複）
- n>30 は `--force` なしでは `[1]` に到達する前にガードで弾かれる（表1と同じ仕組み）

**声かけの参考**: もし参加者が好奇心で n=20 や n=26 を打ってしまっても、慌てず「壊れません、ただ標準RegExp側の待ちが少し長くなるだけです。次は16でやってみましょう」と案内すればよい（技術的には安全）。ただし②完了後は表1に戻る（自作側はどの n でもミリ秒）。

## 4. 詰まりポイントの予告と講師の声かけ

1. **a?b トラップ（①の本丸）**
   症状: `pnpm test` で「a?b」の `m("a?b","b")` だけ赤、他は緑。
   見つけ方: `pnpm exec vitest run -t "a?b"`。
   声かけ: 「**b 単体で落ちてたら連接則の第2項落ち**です。白板見て——∂b(a?b) は第1項 ∂b(a?)·b が ∅ に潰れて、ν(a?)=true だから第2項 ∂b(b)=ε が唯一の生き残り。AIでもこの項は落とすことがある。SPEC の★行をプロンプトに再掲して投げ直してください」
   補足: 「"ab" は第2項なしでも通ります。だから他のテストが緑でも安心しない——このテストが存在する理由です」

2. **AI が①の段階で normalize.ts を勝手に実装してしまう**
   症状: ①直後なのに bench:redos 16 が爆発検知メッセージを出さず、②の驚きが消える。
   見つけ方: ①完了時に全員で `git diff --stat` を打たせ、derivative.ts 以外に差分が出ていないか10秒確認。
   声かけ: 「normalize.ts に差分ある人、`git restore src/normalize.ts` で戻してください。②の伏線なので、ネタバレはいったん巻き戻します」

3. **①直後に `pnpm test:all`（全体）を打って赤に驚く**
   症状: ①完了後、好奇心で `pnpm test` ではなく `pnpm test:all` を打ち、`tests/linear.test.ts` の2件が赤いのを見て「壊れた？」と焦る。
   実際の挙動: ハングはしない。収束ゲートのおかげで一瞬で読める赤（例: `expected 13 to be less than or equal to 5`）が返る。
   声かけ: 「壊れてません、想定通りです。ReDoS 用の状態数テストは**②で緑になる設計**です。①の確認は `pnpm test` で十分（27件全緑ならOK）。`pnpm test:all` は②までは2件だけ赤のままで大丈夫です」

   声かけ: 「エラーが出ないのにマッチしない時は、まず README の対応構文表と照合。基本的にはエラーで教えてくれる設計になってます」
