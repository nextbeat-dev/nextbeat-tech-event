## 事件: 標準の RegExp が長い入力で固まる

```
/^(a+)+$/.test("a".repeat(n) + "X")
```

- n を1つ増やすたびに時間がおよそ倍になる（実測値は当日の実演・README 参照）
- これが **ReDoS**（Regular expression Denial of Service）
- 対して本エンジン（自作）は同じ入力をミリ秒未満で返す
- `pnpm bench:redos <n>` で再現可能（`n` は 30 を超えると `--force` が必要）

---

## なぜ固まるのか① — バックトラックの直観

標準 RegExp は「試して、ダメなら戻ってやり直す」＝**バックトラッキング型**

`(a+)+` に `"aaaa"` を食わせると、エンジンは「a の列を何グループに分けるか」を試す:

```
(aaaa) / (aaa)(a) / (aa)(aa) / (aa)(a)(a)
(a)(aaa) / (a)(aa)(a) / (a)(a)(aa) / (a)(a)(a)(a)
```

末尾が `X` だと全部の分け方が失敗するまで戻り続ける。
**マッチする時は速い。マッチしない時に全経路を確認しに行く。**

---

## なぜ固まるのか② — 分け方は 2^(n-1) 通り

長さ n の `a` の列を連続グループに分割する方法 = **2^(n-1) 通り**（各文字間で「切る/切らない」）

| n | 分け方 |
|---|---|
| 4 | 8 |
| 10 | 512 |
| 28 | 約1.3億 |
| 40 | 約5500億 |

入力が1文字増えるたび**2倍**。これが指数爆発の正体。

---

## 処方箋: 「戻らない」エンジン＝DFA

解決策は昔から知られている: **DFA**（決定性有限オートマトン、deterministic finite automaton）
1文字読むごとに次の状態が一意に決まり、戻る操作を持たない。入力長 n に対して O(n)。

でも教科書の作り方は重い: 正規表現 → NFA（Thompson構成）→ 部分集合構成 → DFA 最小化…

**今日の主役**: Brzozowski 微分（1964）なら、この全部が**再帰関数2つ・約30行**に化ける。
オートマトンの予習は不要。

---

## 発想の転換: 正規表現そのものが「状態」

問い: `abc` にマッチ中、`a` を読み終えた状態って何？
答え: **「残りは `bc` にマッチすればいい」という状態**

```
abc --a--> bc --b--> c --c--> ε(空文字OK) ✅
```

マッチの途中経過は「残りの正規表現」で表せる。**状態＝正規表現そのもの。**

この「1文字食って残りの正規表現を返す」操作を**微分**（derivative）と呼ぶ。

---

## 記号の読み方（この2つだけ）

| 記号 | 読み | 意味 | コードでは |
|---|---|---|---|
| ν(r) | ニュー | r は空文字列 `""` を受理するか | `nullable(r): boolean` |
| ∂c(r) | デル・文字cでの微分 | r を文字 c で微分した残りの正規表現 | `derivative(r, c): Re` |

ついでに: `∅`（空集合＝何も受理しない）、`ε`（イプシロン＝空文字列だけ受理）、`∧`＝かつ、`∨`＝または

数学の微分との関係は気にしなくていい。**ただの関数名。**

---

## 「微分」という名前の理由

積の微分則 `(fg)' = f'g + fg'` は「左を微分した項」＋「右を微分した項」の和。

後で出てくる連接則 `∂c(rs) = ∂c(r)·s | (ν(r) ? ∂c(s) : ∅)` も、
第1項が「左を微分した項」、第2項（`ν(r)` が有効化する）が「右を微分した項」——構造は同型。

**名前は飾りでなく、規則表がこの形で書ける理由そのもの。**

---

## 部品: 正規表現の最小コアは6種類だけ

```
Re = ∅ (Empty)           -- 何も受理しない
   | ε (Eps)             -- 空文字列だけ受理
   | Class(set, neg)     -- 1文字。'a' も [a-z] も . も全部これ
   | Concat(left, right) -- 連接 rs
   | Alt(left, right)    -- 選択 r|s
   | Star(body)          -- 星 r*
```

`+ ? {n,m} ( )` は全部このコアへ**脱糖**: `r+ → r·r*`、`r? → r|ε`。
TypeScript では判別タグ付きユニオン（`src/ast.ts`）。中核は**switch 6分岐で閉じる**。

---

## ν(r) —— 空文字列を受理するか

| r | ν(r) | 理由 |
|---|---|---|
| ∅ | false | 何も受理しない |
| ε | true | 空文字列そのもの |
| Class | false | 必ず1文字消費する |
| r* | true | 0回マッチ（=ε）を含む |
| rs | ν(r) ∧ ν(s) | 両方が空を許して初めて空 |
| r\|s | ν(r) ∨ ν(s) | どちらかが空を許せば空 |

この表が `src/derivative.ts` の `nullable` の switch **6分岐と1対1**。

---

## ∂c(r) —— 文字 c で微分する

「r がマッチする文字列のうち、先頭が c のものから c を1文字剥がした残り」にマッチする正規表現。

| r | ∂c(r) |
|---|---|
| ∅ | ∅ |
| ε | ∅ |
| Class | c ∈ class ? ε : ∅ |
| r* | ∂c(r) · r* |
| rs | ∂c(r)·s **\| (ν(r) ? ∂c(s) : ∅)** ★ |
| r\|s | ∂c(r) \| ∂c(s) |

6行中5行は「見たまま」。★の連接則だけが非自明 → 次のスライドで。

---

## 唯一の非自明ポイント: 連接則の★

`∂c(rs) = ∂c(r)·s | (ν(r) ? ∂c(s) : ∅)` を日本語に分解:

```
rs の先頭の c は、どっちが食べた？
├─ 左の r が食べた   → 残りは ∂c(r)·s      （常にある枝）
└─ 左の r を「0文字でスキップ」して右の s が食べた
                    → 残りは ∂c(s)
                      ただし r が空文字列を許す（ν(r)=true）時だけ！
```

この ν 項を忘れても**大半のテストは通ってしまう**（壊れるのは「左がεを含む連接」だけ）。

---

## 手トレース: `a?b` を `'b'` で微分する

`a?b` は脱糖して `(a|ε)·b`。入力 `"b"` を1文字目 `b` で微分する:

```
∂b( (a|ε)·b )
  = ∂b(a|ε)·b | (ν(a|ε) ? ∂b(b) : ∅)        ← 連接則
    ∂b(a|ε) = ∂b(a) | ∂b(ε) = ∅ | ∅ = ∅      ← 第1項は消える
    ν(a|ε)  = false ∨ true = true             ← ★第2項が生きる
  = ∅·b | ∂b(b) = ∅ | ε = ε
ν(ε) = true → "b" は受理される ✅
```

ν 項を忘れていたら結果は `∅` のまま、`"b"` は不受理になっていた。

---

## このスライドがクライマックス

- `"ab"` は ν 項なしでも通る（∂a(a?b)=b、∂b(b)=ε）
- でも `"b"`（a を0回スキップ）は **ν 項だけが結果を生む唯一の経路**
- だから他のテストが緑のまま、この1件だけ静かに壊れる
- `tests/spec.test.ts` の「a?b トラップ」がこれを検出する

**AI の生成コードが `a?b` テストで赤くなったら、疑う場所は連接則の ν 項一択。**

---

## マッチング＝微分の畳み込み

エンジン全体はこの1行:

```typescript
function match(re: Re, input: string): boolean {
  return nullable(
    [...input].reduce<Re>((state, ch) => derivative(state, ch.codePointAt(0)!), re),
  );
}
```

1文字ずつ微分して、最後に「残りが空文字列を受理するか」を見るだけ。
**「戻る」操作がコード上どこにも存在しない** → バックトラック不能 → この時点で既に線形。

---

## メモ化したら、勝手に DFA になっていた

`match` は毎回微分を計算し直す。→ **微分結果をキャッシュしたら？**

`ab*` の全微分を書き出すと:

```
∂a(ab*) = b*    ∂b(ab*) = ∅
∂a(b*)  = ∅     ∂b(b*)  = b*   ← 自分に戻る！
∂a(∅)   = ∅     ∂b(∅)   = ∅   ← ∅は何を食べても∅
```

出てくる正規表現は **{ab*, b*, ∅} の3つで打ち止め**。
状態＝正規表現、遷移＝微分、受理＝ν。**これは DFA の定義そのもの。**

---

## 遅延DFA: コードにすると数十行

`src/match.ts` の `LazyDfa` の骨格（抜粋）:

```typescript
step(id, c) {
  const cached = row.get(c);
  if (cached !== undefined) return cached;         // 2回目以降: 表引きだけ
  const next = this.intern(derivative(this.states[id], c)); // 初回だけ微分
  row.set(c, next);
  return next;
}
```

「遅延」＝全遷移を先に作らず、実際に来た文字の分だけオンデマンド構築。
実行時は Map 引きのみ。状態＝「ここまで読んだ時点で残っている正規表現」という直観そのもの。

---

## 落とし穴: このままだと状態が爆発する

微分は新しい正規表現を**生み続ける**。素朴にノードを作ると:

```
ε·b* と b*        ← 意味は同じ、構造が違う
r|r と r          ← 意味は同じ、構造が違う
a|b と b|a        ← 意味は同じ、構造が違う
```

キャッシュのキーが一致しない → メモが永遠にヒットしない → **状態が無限増殖**。
`(a+)+` がまさにこれで爆発する（ReDoS を殺すはずのエンジンが別の形で死ぬ）。

もう1つの罠: Map のキーにオブジェクト参照を使うと、同じ構造でも別状態になる。
必ず「正規化後の構造文字列」（`canonicalKey`）をキーにする。

---

## 処方箋: ACI 正規化（スマートコンストラクタ）

生のオブジェクトリテラルでノードを作らず、必ず `mk*` 経由で生成時に等価な形へ潰す:

| 関数 | 規則 |
|---|---|
| mkAlt | `∅\|r=r`（吸収）/ `r\|r=r`（冪等**I**）/ `r\|s=s\|r`（可換**C**→キーでソート）/ フラット化（結合**A**） |
| mkConcat | `∅·r=r·∅=∅`（零元）/ `ε·r=r·ε=r`（単位元）/ 右結合に固定 |
| mkStar | `∅*=ε` / `ε*=ε` / `(r*)*=r*` |

ACI = Associativity・Commutativity・Idempotence。この最小限の正規化で状態が有限個に収まる。

---

## 実測: 入力10倍 → 時間10倍、状態数は一定

`pnpm bench:linear` の出力例（数値は当日実測に差し替え）:

```
pattern = (a+)+   ← 標準RegExpが長い入力で固まるやつ
入力長          所要(ms)   DFA状態数
10,000          ...        2（一定）
100,000         ...        2（一定）
1,000,000       ...        2（一定）
10,000,000      約200      2（一定）
```

読み方: ①入力10倍→時間ほぼ10倍＝**O(n)** ②状態数が入力長に依存しない＝正規化が効いている証拠。

---

## あえて入れないもの: 後方参照 `\1`

`(.+)\1`（同じ文字列の2回繰り返し）のような後方参照は、今日のエンジンには**入れない**。

- 後方参照は正則言語の表現力を**超える** → 有限の状態では原理的に表現できない → DFA化が不可能
- 標準 RegExp がバックトラッキング型なのは、まさに `\1` などをサポートするため
  **表現力と引き換えに ReDoS を抱え込んだ**
- 逆に言うと: **入れないからこそ**線形時間と ReDoS 耐性が「頑張る」ではなく「保証」になる
- 実例: Google RE2 / Rust regex / Go regexp も同じ判断で `\1` 非対応

**「何を入れないかで品質が決まる」**——本日の設計判断の核心。

---

## まとめ & このあとやること

1. 状態＝正規表現そのもの。遷移＝微分 ∂。受理＝ν。**メモ化したら DFA**
2. 非自明なのは連接則の ν 項ただ1つ（`a?b` トラップで検出可能）
3. 正規化（ACI）が状態を有限に抑え、後方参照を入れない判断が線形を**保証**する
